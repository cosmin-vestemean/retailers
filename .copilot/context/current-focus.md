## Confirmed Decisions

- **Infinite RECADV/RETANN filenames are bare numeric IDs with no extension (measured live, session N+17), not `<id>.xml` as previously documented.** The `.xml` suffix seen on every seeded/DB row was added by our own capture scripts (`fetch-recadv-sample.mjs`, the seed script), never by the server. A short-lived exception existed 2026-08-03/04: Dedeman files arrived as `DEDEMAN_RECADV_<id>.xml` (prefixed, with extension). Any future filename-based filtering for these two docTypes must not assume an extension.
- **THE DISPATCH ADVICE IS THE BASE OF COMPARISON, NOT THE RECADV (Sorin Fliundra, 2026-08-05) — IMPLEMENTED session N+19.** Every advice line is now scored; a line the retailer never mentions gets `accepted = 0`, `omittedFromReceipt: true`, i.e. a full shortage — no longer left in unscored `missingOnReceipt` limbo. This was a real defect, not a preference: on `AEX-AE-053715` the advice has 9 lines, Sorin reported TWO products rejected at reception, and the engine reported ONE, because `PF.00133` was simply absent from the RECADV. Financially it matters because we would invoice the full shipped quantity for goods the retailer never received. Pallet/unmapped lines stay excluded (verified — `getAdviceLines` already returns `RETAILERCODE=NULL` for unmapped articles and `reconcileGroup` skips those before they reach `shipped`). **One risk deliberately NOT resolved yet: multi-file receptions are temporal** (4-6 of ~195 in the corpus; a second file arriving next day will show a false full-shortage in between) — no grace period was added because the reconciler has no date data to key one on. Full detail in `/memories/repo/recadv-reception-screen-todo.md`.
- **Invoice XML is sent to Infinite MANUALLY for Dedeman and Auchan — automated/bulk send is OUT of scope (beneficiary, 2026-08-05).** Confirmed again by email the same day: Sorin uploads the file himself and it reaches SPV after 23:00. **But per-invoice `Send`/`Resend` stays in the UI** — a deliberate click on one invoice *is* the manual action; only the bulk `Trimite toate` is suppressed via `manualSend`. Do not remove the per-invoice buttons again.
- **The Facturi tab was blind to Dedeman and Auchan and that is why sending was manual.** `invoice-table.js` hardcoded `fprms=712 / series=7121`, which is every OTHER retailer; Dedeman invoices on **716/7123** and Auchan on **712/7122**, so their tab was simply empty. Proof: **0 of 521** of their invoices in 60 days ever had `CCCXMLSendDate` set. `retailer-detail.js` now carries an `INVOICE_SERIES` map. The app's SFTP send demonstrably **does** work elsewhere (Supeco 156/157, Carrefour 62/64, eMAG 16/24), so manual mode is scoped to the two Infinite retailers, not global. **The SFTP path to Infinite has still never been exercised — the first `Send` there is a test, not a routine.**
- **A shared unfiltered remote directory is scanned once per account per cycle.** Both Infinite config rows point at the same `/recadv`; the guard in `downloadAndStore` keys on `URL|USERNAME|remoteDir` and applies **only** when `prefixes.length === 0`. That condition is load-bearing: `/orders` needs both passes because each config row filters to its own `DEDEMAN_`/`AUCHAN_` prefix, and a blind skip would silently stop ingesting Auchan orders. Locked by a test.
- **Invoicing from a reception is NEVER automatic — it happens only on explicit user action.** Agreed by the beneficiary: „se facturează doar la acțiunea utilizatorului". The reconciliation engine classifies; the operator decides. No phase may add an auto-invoice path without re-opening this.
- **Pallet-only advices are confirmed as non-invoiceable by the beneficiary** — „aceste avize nu se facturează, au valoare 0". Our exclusion in `getReceptionsData` is therefore correct business behaviour, not just noise reduction.
- **The end-to-end chain is proven on production (2026-08-05):** reconciliation reported `AEX-AE-053966` (FINDOC 2180545) clean → the operator invoiced it manually → invoice `FAEXD-PF-40087` (578.75) → the screen flipped that advice to `FACTURAT=1`.
- **RECADV ingestion is gated by `EDI_ENABLE_RECADV`, now set to `true` on `retailers4` (v132).** The flag is read dynamically (`recadvEnabled()` is a getter reading `process.env`), so it remains a config flip, not a deploy. Rollback = unset it; inserted rows are harmless because `INGESTED` is terminal and `processPendingOrders` filters `doctype:'ORDERS'`.
- **RECADV ingestion ships disabled; `EDI_ENABLE_RECADV` is the switch (session N+13).** The plan had F3 adding `recadv` to `docTypes` outright, but `retailers4` runs with `ENABLE_SFTP_SCANNER=true`, so merging that would have started `LIST`/`RETR` on `/recadv` on the next deploy — the exact access that set the portal read-flag — long before the reception screen exists. Only the literal string `'true'` activates it. **F7 is therefore a config-var flip on one app, not a deploy**, which is what F7 steps 2-3 already ask for.
- **RECADV rows get their own terminal status `INGESTED`.** `NEW` means „turn me into a SALDOC" everywhere else in this pipeline; reusing it would be actively misleading even though `processPendingOrders` also filters on `doctype: 'ORDERS'`.
- **`JSONDATA` stores the parsed payload minus `raw`** — `XMLDATA` already holds the source document, so keeping the xml2js tree would double the row for nothing.
- **RECADV routes on `RecadvParty/BuyerParty/GLN`, fail-closed**, reusing `insertRoutingErrorRow` (`TRDR_RETAILER=0`, `XMLSTATUS='ERROR'`, `JSONDATA.routing.reason='unknown_buyer_gln'`). Never fall back to the config row's retailer.
- **Infinite has no `parseAperak`.** Its acknowledgement is RECADV, and RECADV must never reach `CCCAPERAK`. Safe to delete because Infinite never fetched `aperak`: the old prefix filter returned `[]`, which short-circuited the loop before any listing.
- **RECADV never becomes an S1 document.** No FINDOC, no series. It is a notification that *drives* invoices (`7122`/`7123`) and return advices (`9221`) in later phases. Modelling the EDI message as an entity in its own right is precisely what killed the previous developer's `A_IKA_RETANN` / `A_TMP_DEDEMAN_RETANN_*` layer.
- **But the RECADV XML is persisted**, as a `CCCSFTPXML` row with `EDIDOCTYPE='RECADV'` and the parsed payload in `JSONDATA`. The decisive reason is dedup: the scanner checks `XMLFILENAME` **before** downloading, so without persistence it would re-fetch 100+ files every pass and keep re-lighting the portal read-flag forever. Secondary reasons: FTP retention is unknown and untested, and the file is the commercial evidence in a dispute. DO Spaces is only a transient buffer today (the object is deleted once the insert succeeds), so it is not an archive. Zero new tables; `CCCSFTPXML.FINDOC` already exists for the later file↔document link.
- **Reconciliation is computed on demand, not persisted** — at ~250-270 documents/month the cost is trivial and the answer never goes stale when an advice is invoiced later. Only the parsed payload (deterministic) is cached.
- **New AJS modules are allowed**, so RECADV gets its own `S1/JS/AJS/RECADV.js` with bound parameters, instead of pushing pre-built SQL through `processSqlAsDataset1`. Bulk lookups use a single bound parameter + `STRING_SPLIT`, with strict `/^\d{1,15}$/` validation on top as defence in depth. This also keeps `JSRetailers.js` (already 34 functions) from growing.
- **The reception screen is a tab BETWEEN Comenzi and Facturi** in `frontend/src/pages/retailer-detail.js` (today only `orders` / `invoices`).
- **Live FTP download is the LAST step (F7), not the first** — nothing is enabled until the screen that replaces the portal actually works.
- **Real-time push from `EF.js` is parked**, not rejected. If revived in phase 2: `ON_AFTERPOST` (runs **after** commit, so a slow call can never endanger the save), gated on `SALDOC.SERIES` + `TRDR` because it otherwise fires for every sales document company-wide, wrapped in a swallow-everything `try/catch`. Use **`WinHttp.WinHttpRequest.5.1`** — it has `SetTimeouts` and an async mode, whereas `X.HTTPCALL` is synchronous with **no timeout parameter** — with a short `WaitForResponse`, never zero. Not needed for correctness, since the invoiced state is queried on demand.
- **RECADV is implemented now; RETANN waits on Infinite ticket RO-7627.** Beneficiary decision, 2026-08-05.
- **Phase 0 (a Soft1-only „uninvoiced advices" list) is skipped** — the beneficiary will cope in the meantime — and **Infinite is not notified** about the portal read-flag side effect.
- Status machine on CCCSFTPXML.XMLSTATUS: `NEW → PROCESSING → SENT | ERROR`; atomic claim via SQL `UPDATE ... WHERE XMLSTATUS='NEW'`.
- EDIDOCTYPE column populated on insert (`ORDERS`|`RECADV`|`RETANN`|`APERAK`).
- CCCEDIPROVIDER extended with `CODE varchar(20)`, `ISACTIVE bit`; rows updated (docprocess, infinite).
- SQL injection on `{value}` mapping templates closed via AJS `runMappingSql` (rewrites `'{value}'` → `:1` and binds parameter; no DB template migration needed).
- Hardcoded S1 base URLs have been removed from `src/**`. Base URL resolution is now config-driven: explicit request URL when provided, else app config `s1BaseUrl`, else env `S1_BASE_URL`. The EDI order flow still prefers retailer-specific `CCCRETAILERSCLIENTS.WSURL`.
- Scanner safety is stricter now: `ENABLE_SFTP_SCANNER` defaults to `false`, and both automatic scheduling and manual `scanNow` endpoints short-circuit unless explicitly enabled.
- `privateKey.txt` no longer written to disk — `SftpTransport` holds the key in-memory.
- Legacy `sftp` service NOT deleted yet; toggled via `EDI_SCANNER=legacy` for fallback during validation.
